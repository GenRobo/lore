# Linux virtual file system for on-demand workspaces

## Summary

Lore can mount a workspace as a *virtual* file system whose files hydrate on demand rather than
downloading up front, but only on Windows. This proposal adds a Linux backend built on
[FUSE](https://www.kernel.org/doc/html/latest/filesystems/fuse.html) that reaches parity with the
existing Windows ProjFS provider. Crucially, it follows the ProjFS *project-into* model: the mount
overlays a real working directory so that externally-managed files (for example a git working tree)
and Lore-projected files coexist in the same folders, files hydrate lazily on read, and edits to
projected files are intercepted and reported to Lore's modification tracking. The design first
extracts the platform-neutral tree-resolution and content-read logic — today duplicated between the
Windows ProjFS provider (`lore-revision/src/projfs/serve.rs`) and the disabled native SWFS binding
(`lore-revision/src/swfs/serve.rs`) — into a shared VFS core, then implements the Linux mount as a
thin translation shim over that core.

## Motivation

Virtual repositories are a headline capability: a workspace stays lightweight and fetches file data
only when it is read, so a multi-terabyte repository can be worked in without materializing it.
Today that capability stops at the Windows boundary. In `clone_materialize`
(`lore-revision/src/repository/clone.rs`), the `options.virtually` path dispatches to
`crate::projfs::serve::serve(...)` under `#[cfg(all(target_family = "windows", feature = "vfs"))]`,
and every non-Windows target falls through to:

```rust
#[cfg(not(target_family = "windows"))]
{
    lore_error!("Virtual repositories not yet supported on this platform");
    return Err(NotSupported { /* ... */ }.into());
}
```

Linux is where much of the pressure sits: CI runners, build and cook farms, and Linux-based
developer and artist workstations. On all of them a Lore clone must fully hydrate, which negates the
sparse-workspace scaling that is the feature's entire point. A build agent that touches 2% of a
repository still pays to download 100% of it.

The Linux gap is sharper than "same feature, other OS" because of *how* Lore is used alongside other
version control. A common layout keeps source under one system (frequently git) and large binary
assets under Lore, **interleaved in the same directories** — not segregated into asset-only
subtrees. On Windows, ProjFS already serves this: it projects Lore placeholders *into* a real
directory, so a folder can hold `.git`, hand-written source, and a lazily-hydrated Lore asset
side by side, and a write to a projected file is caught and reported back to Lore. Linux has no
equivalent, so a mixed working copy there must fall back to eager hydration and loses the very files
that most need to stay sparse (multi-GB assets).

A second, smaller problem compounds the first. The read logic that walks the merkle tree and streams
content is written twice — once in the live ProjFS provider and once in the dormant SWFS binding —
and the two have already drifted (the SWFS path predates the `VirtualLayer` overlay support and the
`prefetch` option that ProjFS carries). The `vfs` feature is also not exercised by upstream CI, so
the Windows provider bit-rotted against unrelated API refactors and had to be repaired by hand
(commit `445c923`). Adding a third, independently-cfg-gated copy for Linux would compound both the
drift and the silent-rot risk.

## Goals / Non-Goals

### Goals

1. **On-demand lazy read on Linux.** A virtually-cloned workspace on Linux hydrates file content on
   first read, at parity with the ProjFS read path (stat, directory enumeration, ranged content
   reads, prefetch, and `VirtualLayer` overlays).
2. **Coexistence with externally-managed files (project-into).** The mount overlays a real working
   directory so that files Lore does not manage — a git working tree, untracked files, hand-written
   source — pass through and appear in the same folders as Lore-projected placeholders. The mount
   projects *into* the working copy; it does not shadow or replace it.
3. **Edits persist and are tracked.** Modifying, creating, renaming, or deleting a projected file
   under the mount takes effect *and* is reported to Lore's modification tracking, so it appears in
   `lore status` and can be staged and committed rather than silently escaping Lore.
4. **One platform-neutral VFS core.** The tree-resolution and content-read logic lives in a single
   place the Windows and Linux providers both call; ProjFS is re-expressed on it with no behavior
   change, which also repairs the bit-rot and removes the cfg-gated duplication.
5. **Clean mount lifecycle.** Mounting validates and creates the mount point, unmounts cleanly on
   shutdown, and recovers from a stale mount left by a crashed process.
6. **No regression to Windows or to non-virtual clones.** The Linux backend is gated behind the
   existing `vfs` feature and a Linux target cfg; default builds and the ProjFS provider are
   unaffected.

### Non-Goals

- **macOS support.** macOS lacks a bundled FUSE and is better served by an NFS-loopback backend; it
  is deferred to a follow-up. This proposal keeps the neutral core backend-agnostic so that path
  stays open.
- **A new dirty-tracking mechanism.** Write tracking reuses the modification-tracking facility
  proposed in [`2026-05-03-modified-file-tracking.md`](2026-05-03-modified-file-tracking.md), which
  explicitly names VFS providers as its integration target. This proposal consumes that API; it does
  not define its own.
- **eBPF FUSE passthrough (`fuse-bpf` / ExtFUSE).** Cutting per-operation FUSE overhead for
  many-small-files trees is a worthwhile v2 optimization but is kernel-version-gated and out of scope
  for the first landing.
- **On-disk or wire format changes.** The mount reads and writes existing repository state and
  content-addressed data; it introduces no new persisted format.
- **Reviving the native SWFS C library on Linux.** The SWFS binding is Windows-oriented
  (`MOUNT_POINT = "S:"`, `WRITE_PATH = "D:\\swfs-write"`, `bool_ = c_int` FFI). FUSE is the idiomatic
  Linux mechanism; SWFS is not carried forward.

## Proposed Design

### Rebase onto current `upstream/main` first

This branch is behind `upstream/main` (`EpicGames/lore`) by commits this work depends on. Two are
load-bearing and land the change on the correct foundation rather than duplicating it:

- **`80d8197` "Gate `windows-sys` dependencies on Windows targets"** — `lore-revision/Cargo.toml`
  currently declares `windows-sys` as an unconditional dependency, which does not build on Linux at
  all. Upstream already moves it under a Windows target table. The Linux backend cannot compile until
  this lands.
- **`437e727` "Support the service process on Linux and macOS"** (with `9179c6d` for caller
  working-directory resolution) — the mount runs in and alongside the Lore service process, so
  cross-platform service support is the substrate this feature sits on.

Rebasing first is a prerequisite step, not merely hygiene. *Addresses Goal 6.*

### Platform-neutral VFS core

Extract the operations that both existing providers already perform — and that are entirely
OS-agnostic — into a shared module (proposed: `lore-revision/src/vfs/core.rs`). Every backend bottoms
out in the same three primitives, plus prefetch:

- **Resolve + stat** — `State::find_node_link(module, relative_path)` to map a path to a node, then
  `State::node(module, id)` for the `Node` (`size`, `address`, modification time, and `is_file()` /
  `is_directory()`). Used by ProjFS `get_placeholder_info` (`projfs/serve.rs:811`) and SWFS
  `open_file_read`.
- **Enumerate** — walk `Node::child()` / `Node::sibling()` and resolve names via
  `State::block_and_nametable(...)` and `State::node_name_direct(...)`. Used by ProjFS
  `get_directory_enumeration` (`projfs/serve.rs:471`) and SWFS `fill_dir`.
- **Read range** — `immutable::read_into(repository, node.address, Some(range), buf, options)` with
  `immutable::read_options_from_repository(&repository).with_cache()`. Used by ProjFS `get_file_data`
  (`projfs/serve.rs:967`) and SWFS `read_file`.
- **Prefetch** — `State::cache_fragments(repository)` and the `prefetch_files(...)` warm-up spawned at
  mount time (`projfs/serve.rs:1133`).

The core exposes these as backend-agnostic async functions returning neutral types (`NodeMeta`,
`DirEntry { name, kind, size, mtime, node_id }`, byte counts) and encapsulates `VirtualLayer` overlay
resolution (`projfs/serve.rs:106,318`). Because `RepositoryContext.path` is `Option<PathBuf>`
(`repository.rs:521`), the core resolves the working-directory root through `require_path()`
(`repository.rs:619`) and surfaces its absence as a typed error the backend maps to its native
failure — the same refactor a recent fix applied to ProjFS (commit `445c923`) after that module was
left behind by the `Option`-path change.

Re-expressing ProjFS on this core is behavior-preserving and doubles as the vehicle for repairing the
bit-rot: because the `vfs` feature is not built by upstream CI, the Windows provider silently fell out
of sync with unrelated API changes. Consolidating onto one core surface means a future refactor breaks
one place loudly rather than one cfg-gated copy quietly. *Addresses Goal 4.*

### Coexistence: project into the working directory

The mount does not present the Lore tree in isolation; it overlays a *real* working directory and
presents a union of two sources:

- **Pass-through** — entries that exist on the backing directory (a git working tree, `.git`,
  untracked files, previously materialized files) are served from the real filesystem unchanged, so
  non-Lore tooling sees exactly what it wrote.
- **Projection** — entries that exist in Lore state but not on disk are presented as lazily-hydrated
  placeholders resolved through the neutral core.

This is the harder half on FUSE and is the reason a plain mount-over cannot be used (see Alternatives):
a mount-over would shadow the git files at the mountpoint, breaking coexistence. The union must merge
the pass-through listing with the projected listing on `readdir`, resolve `lookup`/`getattr` against
whichever source holds the name (pass-through wins for names present on disk), and route `open`/`read`
to the real file or the projected content accordingly. ProjFS provides this on Windows by construction
(it projects into a real directory); the Linux backend must implement the union explicitly. The
Meta EdenFS/Sapling design and the Rust union/copy-on-write FUSE work in `scorpiofs` (built for
git-monorepo virtual filesystems) are direct references or candidate building blocks and should be
evaluated before writing a union layer from scratch. *Addresses Goal 2.*

### Linux backend: FUSE

Implement the mount in `lore-revision/src/vfs/fuse.rs`, gated to Linux and the `vfs` feature, on the
[`fuser`](https://github.com/cberner/fuser) crate (the maintained successor to `fuse-rs`); the
async-oriented [`fuse-backend-rs`](https://github.com/cloud-hypervisor/fuse-backend-rs) is a candidate
if the union/writeback layer benefits from its model. `fuser` provides a `Filesystem` trait and a
`spawn_mount2` that runs the session on a background thread. The read path maps as follows:

| Neutral core op | ProjFS callback              | FUSE method                        |
| --------------- | ---------------------------- | ---------------------------------- |
| resolve + stat  | `get_placeholder_info`       | `lookup`, `getattr`                |
| enumerate       | `get_directory_enumeration`  | `opendir`, `readdir`, `releasedir` |
| read range      | `get_file_data`              | `open`, `read`, `release`          |
| existence check | `query_file_name`            | folded into `lookup`               |
| prefetch        | `prefetch_files`             | spawned at mount                   |

Two mechanics are specific to FUSE:

- **Inode table.** ProjFS and SWFS key operations off path strings; FUSE keys off `u64` inodes. The
  backend maintains a `NodeID ⇄ inode` map (spanning both pass-through and projected entries),
  populated during `lookup`/`readdir` and consulted by `getattr`/`open`/`read`. This is the main
  net-new data structure. Node modification times convert to `SystemTime` directly, avoiding the
  Windows FILETIME epoch arithmetic (`lore_time_to_ms_time`, `swfs/serve.rs`).
- **Sync-to-async bridge.** `fuser` callbacks are synchronous on libfuse threads. Each bridges to
  Lore's async core with `runtime().block_on(LORE_CONTEXT.scope(execution_context(), ...))`, exactly
  as ProjFS and SWFS already do (`projfs/serve.rs`, `swfs/serve.rs:499`).

*Addresses Goal 1.*

### Writeback overlay and modification tracking

ProjFS lets real writes land on disk and only *virtualizes* not-yet-hydrated files; it then subscribes
to kernel notifications (`PRJ_NOTIFY_NEW_FILE_CREATED | PRJ_NOTIFY_FILE_RENAMED |
PRJ_NOTIFY_FILE_HANDLE_CLOSED_FILE_MODIFIED | PRJ_NOTIFY_FILE_HANDLE_CLOSED_FILE_DELETED`,
`projfs/serve.rs:296`) to learn what changed. FUSE has no such split: it intercepts every syscall, so
the backend must define write behavior explicitly. Because coexistence (Goal 2) requires editing
projected Lore files *in place* and having Lore track the edit (Goal 3), writeback is mandatory here,
not a deferrable enhancement — a read-only union would push edits into the pass-through side, decoupled
from Lore.

This proposal serves writes from a **scratch overlay directory** (the FUSE analogue of the SWFS
`write_dir`):

- `read` prefers overlay content when a projected file has local modifications, and otherwise hydrates
  from the content store through the neutral read op.
- `write`, `create`, `mkdir`, `unlink`, `rename`, and `setattr(size/mode/mtime)` operate on the
  overlay, copying a hydrated baseline into the overlay on first write (copy-up).
- On `release` of a modified handle — and immediately for `create`/`unlink`/`rename` — the backend
  translates the change into a `lore file dirty` call
  ([`2026-05-03-modified-file-tracking.md`](2026-05-03-modified-file-tracking.md)): modify/add for
  writes and creates, delete for unlinks, and the explicit `move` subcommand for renames. That LEP
  designs this API precisely for "a VFS provider that intercepts write, rename, and delete callbacks
  from the kernel," so the mount records modifications without a filesystem scan and they surface in
  `lore status`, stage, and commit.

*Addresses Goal 3.*

### Mount lifecycle and wiring

`serve()` currently ends in an infinite `loop { sleep }` that never returns (`swfs/serve.rs`; ProjFS
is analogous). The Linux backend instead holds the `fuser` background session and blocks on a shutdown
signal; on shutdown or drop it unmounts (with a `fusermount3 -u` fallback) so no stale mount is left
behind. On mount it validates and, if needed, creates the mount point, and if a stale Lore mount is
already present it unmounts and recovers before proceeding. The `clone_materialize` dispatch gains a
Linux arm alongside the existing Windows one, matching the established call-site signature
`serve(path, repository, state, layers, prefetch)`:

```rust
#[cfg(all(target_os = "linux", feature = "vfs"))]
{
    crate::vfs::fuse::serve(_path, repository.clone(), state, layers, options.prefetch.as_deref());
}
```

Other non-Windows targets (macOS) keep the existing `NotSupported` error until the NFS path lands.
*Addresses Goals 5 and 6.*

### Delivery phases

1. **Neutral core + repair ProjFS.** Extract resolve/enumerate/read/prefetch into the core; re-express
   `projfs/serve.rs` on it so there is a working reference on the platform where projection already
   exists. (Goals 4, and the read half of 1.)
2. **Linux FUSE: project-into + lazy read.** Union pass-through with projected placeholders and hydrate
   on read; validate mixed git+Lore coexistence and on-read hydration against a live server. (Goals 1
   and 2.)
3. **Writeback.** Intercept writes into the scratch overlay and report via `lore file dirty` so edits
   surface in `lore status`/stage/commit. (Goal 3.)

## Compatibility

- **Wire format** — N/A. The mount is a local presentation of already-fetched or on-demand-fetched
  state; it changes no serialization, framing, or compression.
- **Client/server protocols** — N/A. Mounting is a local operation. Content hydration uses the
  existing transport and RPCs unchanged; no new request/response shapes.
- **On-disk format** — N/A. The mount reads existing repository state and content-addressed data and
  writes user edits to a scratch overlay outside the repository format. Modification tracking reuses
  the `Dirty` flag and staged anchor defined by the modified-file-tracking LEP; this proposal adds no
  new persisted structure.
- **CLI and public API** — Additive. A new build feature enables the backend, and virtual clone begins
  succeeding on Linux where it previously returned `NotSupported`. Any mount management surface (see
  Unresolved Questions) is new and additive. No existing command syntax, exit code, or output format
  changes.

## Non-Functional Considerations

- **Concurrency** — libfuse dispatches callbacks on multiple threads. Each callback bridges to the
  async core with `block_on`, so per-operation the model matches the existing providers. The inode
  table is shared mutable state guarded by a lock (`parking_lot::Mutex`, as the SWFS `INSTANCE`
  already uses). Overlay writes for a single path are serialized by the kernel's per-inode locking;
  cross-path writes proceed concurrently. Concurrent modification reporting inherits the single-writer
  staged-anchor model documented in the modified-file-tracking LEP.
- **Memory** — Reads stream through `immutable::read_into` with an explicit byte range, so no
  whole-file buffering is introduced; memory is bounded by the kernel read size, matching ProjFS. The
  inode table grows with the number of *touched* nodes, not repository size, and is the only
  persistent allocation the backend adds.
- **Statelessness** — A live mount is inherently stateful: it holds the background session and the
  inode table for the process lifetime. That state is scoped to the mount and torn down on unmount; it
  is documented as a per-mount, in-process resource and is not persisted.
- **Determinism** — The same repository state produces the same directory tree, file sizes, and
  content; the union resolves name collisions deterministically (pass-through wins). Modification
  tracking is deterministic given the same sequence of write callbacks, per the modified-file-tracking
  LEP.

## Migration Plan

N/A — no breaking changes, no migration required. The backend is opt-in behind the `vfs` feature and a
Linux target cfg. Non-virtual clones and the Windows provider are unaffected, and the neutral-core
refactor is behavior-preserving.

## Security Considerations

A FUSE mount exposes repository content at a filesystem path. By default the mount is single-user (no
`allow_other`), so only the mounting user can read it; enabling cross-user access is an explicit,
documented opt-in that also requires `user_allow_other` in `/etc/fuse.conf`. A crafted repository is
the sharpest concern: node names that contain path separators or `..` could, if passed through
naively, let enumeration or lookup escape the mount root, and — because the mount projects into a real
working directory — could collide with or mask pass-through files. The neutral core must reject or
sanitize such names — the existing providers normalize and trim separators (`open_dir` in
`swfs/serve.rs` shows the pattern) — and the FUSE backend operates per-inode with names validated on
`lookup`, which structurally prevents traversal. The scratch overlay is created with owner-only
permissions so hydrated and in-progress content is not world-readable. Content integrity is unchanged:
reads go through the existing content-addressed store and its verification.

## Privacy Considerations

The mount presents file paths and content that are already local to the machine, so it exposes no new
data to server operators, peers, or telemetry. The one new exposure vector is `allow_other`, which
would make mount content visible to other local users; it is off by default and gated behind explicit
configuration. The scratch overlay holds user edits locally, is owner-only, and is removed on unmount,
so it introduces no new retention or redaction surface beyond the working directory a non-virtual clone
already creates.

## Risks and Assumptions

**Assumptions**

- **Assumption:** Target Linux hosts provide libfuse3 and `/dev/fuse` (via `fusermount3`). *Invalidated
  if:* deployment targets are locked-down containers without `/dev/fuse` or the `SYS_ADMIN` capability,
  in which case those hosts fall back to full hydration. (Verified present on the Linux development
  host: `/dev/fuse` and libfuse3 3.14.)
- **Assumption:** The modified-file-tracking `file dirty` API
  ([`2026-05-03-modified-file-tracking.md`](2026-05-03-modified-file-tracking.md)) lands and is the
  supported way for a provider to report changes. *Invalidated if:* that LEP is rejected or its API
  shape changes materially, which would force the writeback path onto a different reporting mechanism.
- **Assumption:** Presenting the union as pass-through-plus-projection is sufficient for coexisting
  version-control tooling (e.g. git) to operate normally on its own files under the mount. *Invalidated
  if:* a coexisting tool depends on filesystem semantics FUSE cannot faithfully reproduce for its
  pass-through files (specific `ioctl`s, inotify guarantees, hardlink identity).

**Risks**

- **Risk:** A FUSE callback that blocks in `block_on` while the async work itself waits on the same
  runtime could starve or deadlock the mount under load. *Mitigation:* serve callbacks on a dedicated
  runtime with bounded worker threads, matching how the existing providers isolate their blocking
  bridge, and keep per-callback work to a single awaited operation.
- **Risk:** A crashed Lore process leaves a stale mount that blocks the next mount at the same point.
  *Mitigation:* detect an existing Lore mount at startup and unmount-then-remount before serving;
  expose a manual unmount path.
- **Risk:** The `vfs` feature is not built by upstream CI, so the Windows provider already bit-rotted
  once (commit `445c923`) and a Linux backend could rot the same way. *Mitigation:* the neutral-core
  consolidation reduces the cfg-gated surface to one shared module, and this proposal adds a
  `cargo build --features vfs` compile check plus a FUSE integration suite (below) to exercise it.
- **Risk:** CI Linux runners without FUSE cause the integration tests to fail spuriously. *Mitigation:*
  gate FUSE integration tests behind a runtime capability check for `/dev/fuse` and skip with a clear
  message when absent; keep the neutral-core unit tests kernel-free.

## Drawbacks

- The Linux backend adds a runtime system dependency on libfuse3 and `/dev/fuse` access, which not
  every host or container grants.
- The writeback overlay introduces a scratch region whose lifecycle (copy-up, cleanup on unmount,
  reconciliation after a sync moves the baseline) must be managed and is a source of edge cases a
  read-only mount would avoid.
- The union (pass-through + projection) is materially more complex than presenting the Lore tree alone
  — name-collision rules, listing merges, and per-inode source routing must all be correct — but
  coexistence (Goal 2) makes it unavoidable.

## Alternatives Considered

### Status quo — full hydration on Linux

Leave Linux on the `NotSupported` path and require a full clone.

*Rejected because:* it forfeits the sparse-workspace scaling that motivates virtual repositories, on
exactly the hosts (CI, build farms) where the download cost hurts most. A build agent touching a
fraction of a repository would still pay to materialize all of it.

### Shadow-only FUSE mount-over

Mount a FUSE filesystem *over* the working directory that presents only the Lore tree, without merging
in the underlying real files.

*Rejected because:* mounting over a directory hides its existing contents, so a coexisting git working
tree at the mountpoint would be shadowed — failing coexistence (Goal 2). Empirically, the Windows
reference (ProjFS) does the opposite: it projects *into* a real directory so git files and Lore
placeholders appear together. The Linux design must match that, which is why it commits to an explicit
union rather than a mount-over.

### OverlayFS + read-only lazy FUSE

Use kernel `overlayfs` with the git working tree as the upper layer and a read-only lazy-hydrating FUSE
mount (of the Lore tree) as the lower layer — the SOCI/Nydus lazy-container pattern.

*Rejected as the primary mount because:* it delivers coexistence and lazy *reads* cheaply (the kernel
unions the layers), but a write to a projected Lore file copies-up into the git-side upper layer,
decoupled from Lore — so the edit never enters Lore's tracked set, failing Goal 3 without an explicit
out-of-band reconcile. It remains attractive as a **read-only consumer fast path** (CI jobs, ephemeral
pods that never edit Lore files), and the neutral core makes offering it later straightforward; it is
not the foundation for the edit-capable mount.

### NFS-loopback backend (e.g. `nfsserve`)

Serve the workspace over a localhost NFS server the kernel mounts, avoiding a libfuse dependency.

*Rejected because:* on Linux it adds an NFS protocol layer and its latency where FUSE talks to the
kernel directly, and it needs a privileged mount or a less consistently-available unprivileged NFS
path. It remains the right choice for macOS, so the neutral core is kept backend-agnostic to enable it
there later rather than adopting it for Linux now.

### Reuse the native SWFS C library on Linux

Build and link the existing SWFS binding (`swfs/serve.rs`, `swfs.rs`) on Linux.

*Rejected because:* the binding is Windows-shaped (drive-letter mount point, Windows file attributes,
`bool_ = c_int` return convention) and ships no Linux target; it also predates `VirtualLayer` and
`prefetch`. Reaching parity would mean porting a C library and its bindgen surface when FUSE is the
idiomatic, dependency-light Linux mechanism.

## Prior Art

- **Sapling / EdenFS** (Meta) is the closest analogue and the design to study directly: a virtual
  filesystem for source control that presents a lazily-hydrated working copy backed by a content store,
  using **FUSE on Linux, NFS on macOS, and ProjFS on Windows** behind one backend-neutral core — the
  same three-backends-one-core shape and the same Linux/macOS split this proposal adopts. Its working
  tree *is* the mount, which is exactly the project-into model Goal 2 requires.
- **`scorpiofs`** (`web3infra-foundation/scorpiofs`) is a Rust async-FUSE implementation with a
  union/copy-on-write overlay purpose-built for git-monorepo virtual filesystems. It targets nearly
  this exact problem in this language and is a candidate reference or building block for the union and
  copy-up layers.
- **VFS for Git / Scalar** (Microsoft) pioneered the ProjFS approach on Windows and a modified-paths
  list populated by the projection provider's change callbacks — the model Lore's ProjFS provider and
  the modified-file-tracking LEP already mirror. Its Windows-only origin is precisely the gap this
  proposal closes on Linux.
- **Perforce** uses explicit `p4 sync`/`have` state rather than lazy hydration; it demonstrates the
  cost this proposal avoids — the user must declare up front what to materialize instead of files
  appearing on read.
- **Not a fit:** `gitfs` mounts *git* through FUSE (the opposite direction — exposing a git repo as a
  filesystem, not projecting a content store into a working copy); `libprojfs` (a Linux ProjFS-API
  shim) is archived and unmaintained.

## Unresolved Questions

- **Mount management surface.** Does virtual clone block for the mount's lifetime (as `serve()` does
  today), or should there be explicit `lore mount` / `lore unmount` commands and a daemonized mount?
  This affects the service-process integration and the lifecycle design.
- **Union building block.** Adopt `scorpiofs`'s union/COW layer (or `fuse-backend-rs`) as a dependency,
  or implement the pass-through-plus-projection union directly against `fuser`? The choice trades a
  dependency and its model against control over collision and copy-up semantics.
- **`allow_other` policy.** Should cross-user mounts ever be enabled by default for shared build agents,
  or always require explicit opt-in plus `/etc/fuse.conf`?
- **Overlay reconciliation after sync.** When a sync moves the committed baseline while overlay edits
  exist, how does copy-up reconcile — rebase the overlay onto the new baseline, or surface a conflict
  through the modification-tracking state?
